# Remote save-participant readiness candidate

This temporary sibling harness keeps the ordinary nine source inputs and frozen
save-action baseline intact while a setup change receives genuine remote evidence.
It uses the pinned 1.95.0 product and the exact original 14-case corpus. The only
changed executable inputs are `save-code-actions.cjs` and its worker. The sibling
has the same repository depth, so its existing product-cache paths remain valid.

Before explicit target saves, a separate unshown `readiness.ini` document receives
bounded setup edits and actual saves until its exact null-formatter callback proves
save-participant installation. Only this auxiliary language enables format-on-save.
The original target disk and effective configuration remain asserted; each original
target command executes once. After-delay fixtures skip this explicit-save witness.
Readiness attempts and callbacks are retained separately in evidence. The whole
setup deadline is five seconds with at most 16 attempts; failure aborts capture.

Controlled Node tests cover late installation, stale/foreign/canceled callbacks,
duplicates, deadlines and failed preconditions. These tests do not establish actual
reference behavior. The dedicated GitHub workflow captures each remote platform
once and archives output, logs and immutable input bytes even on failure. No local
VS Code launch is required or authorized. Existing frozen evidence is not edited.

Do not select this observer as the default until complete genuine captures and a
strict native auxiliary-evidence preflight qualify it. Preserve differing target
observations and diagnose them; do not retry a target to obtain preferred output.
The source-supported lifecycle race remains a hypothesis until remote evidence
supports the new setup. This is reference-harness work, not new editor parity.
